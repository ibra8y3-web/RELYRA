# المرحلة العاشرة — مختبر الأجهزة الحقيقية والتحقق متعدد الهواتف

**النطاق الحاكم:** هذه المرحلة مخصصة للتحقق على أجهزة Android فعلية مستقلة، وليست مرحلة إضافة بروتوكول شبكة جديد أو إعادة بناء أنظمة موجودة. لا تُعامل اختبارات المحاكي على أنها اختبار أجهزة حقيقية.

## ما أُضيف إلى المستودع

- companion/node/src/device-lab.mjs: اكتشاف أجهزة ADB الفعلية، استبعاد المحاكيات، قراءة ملف الجهاز والبطارية ونوع النقل وإصدار RELYRA، وتشغيل اختبارات Android Instrumentation على كل جهاز بالتتابع.
- companion/node/bin/relyra.mjs: أوامر device-lab inventory وdevice-lab run.
- companion/node/test/device-lab.test.mjs: اختبارات محلل ADB، واكتشاف المحاكيات، وقراءة البطارية والشبكة، وتنقيح معرّفات الأجهزة.
- app/src/androidTest/java/org/relyra/app/Phase10PhysicalDeviceProfileTest.kt: اختبار Instrumentation يلتقط مواصفات الجهاز الفعلي وقدرات Android من داخل التطبيق. يتخطى المحاكيات تلقائيًا.
- تقرير JSON وMarkdown وقائمة CSV للحالات اليدوية، تُنشأ محليًا داخل .relyra-device-lab/ بصلاحيات ملفات مقيدة.

## المتطلبات

- جهازان Android فعليان على الأقل، بهويتين مستقلتين، مع تفعيل USB debugging والموافقة على مفاتيح ADB.
- Android SDK / Platform Tools (adb) وGradle 9.6.0 وJava 17.
- بناء نسخة Debug من المصدر الحالي.
- لا تحفظ أرقامًا تسلسلية أو عناوين IP أو MAC أو SSID أو محتوى رسائل أو مفاتيح خاصة ضمن التقارير.

## التشغيل

من جذر المستودع:

~~~bash
node companion/node/bin/relyra.mjs device-lab inventory
node companion/node/bin/relyra.mjs device-lab run
~~~

يحتاج run إلى جهازين فعليين على الأقل. لتجربة تجهيز جهاز واحد فقط دون إغلاق المرحلة:

~~~bash
node companion/node/bin/relyra.mjs device-lab run --allow-single-device
~~~

يُشغّل الأمر :app:connectedDebugAndroidTest مرة لكل جهاز باستخدام ANDROID_SERIAL، ثم ينشئ:
- phase10-report.json
- phase10-report.md
- manual-checklist.csv

المحاكيات والأجهزة غير المصرح بها لا تدخل في قائمة الأجهزة الفعلية. لا يثبت نجاح Instrumentation وحده نجاح الاتصال بين هاتفين.

## مصفوفة التحقق اليدوي الإلزامية

1. اقتران هويتين مستقلتين والتحقق من بصمات الهوية.
2. الرسائل الفردية وإيصالات التسليم ومنع تكرار الرسالة عند إعادة الإرسال.
3. إنشاء مجموعة MLS وإرسال الرسائل وتحديث epoch وإضافة/إزالة الأعضاء.
4. إضافة جهاز موثوق وإلغاءه والتحقق من رفض الجهاز الملغى على جميع المسارات.
5. إرسال واستقبال مرفقات مشفرة، وفحص الحجم والبصمة وسلوك الملفات الكبيرة.
6. إنشاء نسخة احتياطية على جهاز واستعادتها على جهاز آخر والتحقق من تنظيف حالة Ratchet القديمة.
7. مكالمات صوتية ثنائية الاتجاه عبر Wi-Fi.
8. مكالمات فيديو، ورفض أذونات الكاميرا/الميكروفون ثم منحها لاحقًا.
9. الانتقال بين Wi-Fi وبيانات الهاتف أثناء الرسائل والمكالمات.
10. NAT مقيد مع خادم TURN منشور فعليًا، واختبار allocation وانتهاء بيانات الاعتماد وإعادة الاتصال.
11. التسليم بالخلفية أثناء Doze وتحسين البطارية.
12. قتل العملية وإعادة تشغيل الهاتف وتحديث التطبيق ثم التحقق من استعادة الحالة.
13. Mesh متعدد القفزات عبر BLE مع تعطيل الإنترنت.
14. Wi-Fi Direct وNearby LAN مع مصافحة الهوية الموقعة.
15. العربية RTL وTalkBack وتكبير النص والإشعارات.

## قواعد تسجيل النتائج

- اكتب PASS فقط بعد تنفيذ السيناريو على الأجهزة المحددة وحفظ دليل قابل لإعادة التحقق.
- اكتب FAIL مع إصدار التطبيق وطراز الجهاز وإصدار Android ونوع الشبكة وخطوات إعادة الإنتاج.
- اكتب BLOCKED عند غياب خادم أو جهاز أو إذن مطلوب.
- اترك الحالة PENDING إذا لم يُنفذ الاختبار. لا تحوّل اختبارات المحاكي إلى نجاح مادي.
- لا ترفق سجلات تحتوي على أسرار أو بيانات شخصية. التقارير التي ينشئها المختبر لا تتضمن سجلات الرسائل أو معرفات الشبكة الحساسة.

## ما لا يمكن إغلاقه من دون أجهزة فعلية

لا يستطيع CI السحابي أو هذا المساعد ادعاء اختبار هاتفين مستقلين دون وجودهما فعليًا واتصال ADB بهما. الأداة والاختبارات ومصفوفة التحقق أصبحت جزءًا من المشروع؛ أما نجاح الحالات متعددة الأجهزة فيظل معلقًا حتى توصيل الهواتف وتشغيل المختبر وتسجيل نتائج كل حالة.

كما أن نجاح هذه المرحلة لا يغلق تلقائيًا بوابة تدقيق المرحلة التاسعة؛ تنبيه DHT الأمني ومراجعات التراخيص والأمان المستقلة تظل منفصلة.
