# RELYRA — مطابقة المواصفات وحالة التنفيذ

هذا الملف يربط الأقسام الـ50 من المواصفات بحالة الكود الفعلية في المستودع. وجود اسم وحدة أو شاشة أو بند في الخطة لا يعني أن الوظيفة منفذة. الحالة هنا مبنية على المصدر الموجود، وليست اعتمادًا نهائيًا بعد اختبار الأجهزة.

## معاني الحالات

- **موجود:** الوظيفة الأساسية لها تنفيذ في المصدر.
- **جزئي:** يوجد جزء عامل، لكن عناصر مهمة من المواصفة لم تنفذ أو لم تُختبر.
- **غير منفذ:** لا يوجد تنفيذ فعلي في الإصدار الحالي.
- **مضاف في هذا التحديث:** إضافة تنفيذ أو إعداد حقيقي في فرع هذا التحديث، ويظل بحاجة إلى نجاح CI والدمج قبل اعتباره ضمن `main`.

## إضافات أدوات المستخدم في هذا التحديث

- عارض ويب داخلي بقبول HTTP/HTTPS فقط، مع تعطيل JavaScript وCookies وDOM Storage والوصول إلى الملفات المحلية والمحتوى المختلط، وإلغاء أخطاء شهادات TLS.
- قارئ PDF محلي للقراءة فقط يعرض صفحة واحدة في كل مرة من `PdfRenderer` دون رفع الملف.
- اختبارات JVM لسياسة قبول عناوين الويب ورفض مخططات `file:`, `content:`, `javascript:` و`intent:`.
- حدود واضحة: العارض ليس Tor أو متصفحًا مجهول الهوية؛ ولا يتضمن قارئ PDF بحثًا أو تعليقات أو تحريرًا.

## إضافة الاتصال المحلي في هذا التحديث

- موصل Nearby LAN اختياري، ومغلق افتراضيًا.
- يعلن المعرّف العام عبر Android NSD/mDNS على الشبكة المحلية، ويعتمد فقط جهات الاتصال المعروفة الموجودة في دفتر الاتصال.
- ينقل حزم DeliveryEngine المشفرة مسبقًا ويستقبلها عبر `DeliveryEngine.onWire`؛ لا يفك التشفير داخل طبقة الشبكة المحلية.
- يسبق Nostr في ترتيب AdaptiveRouter، ويظل Nostr احتياطيًا عند عدم وجود نظير محلي.
- الحدود: Nearby LAN يحتاج نفس شبكة IP أو نقطة اتصال. Bluetooth Classic يحتاج اقتران Android مسبقًا، وWi-Fi Direct يحتاج تكوين مجموعة P2P. لا يوجد اتصال عبر الإنترنت بين شبكات منفصلة أو نقل متعدد القفزات. اختبار جهازين حقيقيين ما زال مطلوبًا.

## إضافات الاتصال القريب في هذه الدفعة

- موصل Bluetooth Classic عبر RFCOMM للأجهزة المقترنة مسبقًا من إعدادات Android؛ لا يوجد BLE scan أو اقتران من داخل التطبيق.
- موصل Wi-Fi Direct يستعمل Android WifiP2pManager لاكتشاف الأجهزة وتكوين مجموعة اتصال، ثم TCP داخل شبكة المجموعة.
- مصافحة مشتركة بتحدٍ عشوائي موقّع Ed25519 في الاتجاهين؛ لا تُقبل هوية لمجرد اسم الجهاز أو عنوان MAC، ويجب أن تكون جهة اتصال معروفة وغير محظورة.
- تمر الحزم المشفرة طرفًا لطرف إلى DeliveryEngine فقط؛ حد الإطار 256 KiB، وتستخدم الملفات مسار Blossom الحالي بدل إرسال الملف كاملًا في الإطار.
- أضيفت إعدادات وصلاحيات Android وواجهات عربية/إنجليزية واختبارات JVM للمصافحة.
- الحدود: يلزم فحص CI واختبار جهازين فعليين لمسار WebRTC. يوجد Internet P2P تجريبي عبر ICE/STUN/TURN، لكنه لا يوفر DHT أو LibP2P أو NAT traversal متعدد المسارات أو Mesh Store & Forward عبر أجهزة وسيطة. قائمة التسليم المحلية وإعادة المحاولة وNostr backlog لا تعني أن الأجهزة المجاورة تعمل كمرحلات رسائل للآخرين.

## ما أُضيف في التحديث السابق

1. **ResourceManager حقيقي:** يقرأ زمن CPU لعملية RELYRA، وعدادات حركة الشبكة الخاصة بمعرف UID للتطبيق، ومساحة التخزين المتاحة في نظام ملفات التطبيق.
2. **مراقبة مباشرة:** شاشة التشخيص تعرض قراءات كل ثانيتين، مع توضيح أن حركة الشبكة تخص التطبيق فقط.
3. **تعامل آمن مع عدم توفر القياسات:** لا يحوّل عدادات Android غير المدعومة أو أول عينة إلى أرقام صفرية مضللة.
4. **اختبارات حسابات:** تحقق من تطبيع CPU ومعدلات نقل البيانات وإعادة ضبط العدادات.
5. **توثيق المطابقة:** هذا الجدول يوضح الواقع الحالي مقابل كل بند.
6. **ملفات المشروع المفتوح:** Apache-2.0 وDependabot وSecurity/Contribution guidance.

## إضافة Tor SOCKS في هذه الدفعة

- إعداد وكيل SOCKS5 محلي اختياري مع منفذ افتراضي 9050، يعمل مع عميل OkHttp المشترك لطلبات Nostr وBlossom.
- وضع Strict يعرض مسار SOCKS فقط ولا يضيف DIRECT كمسار احتياطي؛ الوضع غير الصارم يسمح بالتحويل المباشر ويحذر من كشف IP.
- إعادة فتح اتصالات Nostr WebSocket عند تغيير إعداد Tor.
- اختبار حقيقي عبر Tor Project API يتحقق من IsTor ويعرض عنوان خروج Tor.
- حظر WebView المدمج أثناء تفعيل وكيل Tor لأنه لا يستخدم وكيل OkHttp.
- الحدود: يحتاج التطبيق إلى Tor service خارجية مثل Orbot؛ إدارة Bridges تبقى في خدمة Tor. لا يمر Bluetooth أو Wi-Fi Direct أو LAN عبر Tor، ولا توجد Onion Services أو Tor daemon مدمج.

## ما لا يجوز اعتباره منجزًا بعد

لا تعتبر Internet P2P أو LibP2P أو NAT Traversal أو Bluetooth/Wi-Fi Direct على أجهزة فعلية أو Store & Forward عبر وسيط أو Tor daemon/Bridges داخل RELYRA أو MLS أو WebRTC أو Matrix/XMPP أو المجتمعات أو Local API أو Plugin SDK أو مزامنة الأجهزة مكتملة لمجرد وجود الكود أو ذكرها في هذا الملف. كل واحدة تحتاج تنفيذًا مستقلًا واختبارات بروتوكول وتكامل وأجهزة حقيقية.


## تحديث المرحلة الثانية — WebRTC P2P

- أضيف موصل WebRTC إلى AdaptiveRouter قبل المسارات القريبة وNostr.
- أضيفت واجهة إنشاء عرض الاتصال، وإرسال الإشارات تلقائيًا داخل رسائل E2EE عبر Relay Nostr المتاح، مع نسخة يدوية احتياطية؛ التوقيع Ed25519 والمستلم ومعرّف الجلسة ومدة الصلاحية يتم التحقق منها.

- تنتقل حزم DeliveryEngine المشفرة مسبقًا عبر DataChannel ثنائي موثوق ومرتب، مع حد 64 KiB للإطار.
