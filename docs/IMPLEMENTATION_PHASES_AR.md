# RELYRA — خطة التنفيذ وترتيب الإغلاق

> المرجع الحاكم للحالة الفعلية هو [جرد الفرع الرئيسي](MAIN_BRANCH_AUDIT_AR.md). لا تعتمد على README قديم أو أسماء الفئات وحدها لإعلان اكتمال أي وظيفة.

## قواعد إلزامية
1. راجع التنفيذ الموجود قبل كتابة أي ملف. لا تعِد بناء ميزة موجودة.
2. كل ميزة يجب أن تكون حقيقية ومربوطة بواجهة التطبيق ومسار الاستخدام المناسب، وليس مجرد مكتبة أو شاشة غير موصولة.
3. لا أزرار شكلية ولا بيانات وهمية ولا وعود تشغيل غير مختبرة.
4. كل تغيير يشمل اختبارات مناسبة وتوثيقًا عربيًا وإنجليزيًا.
5. لا تختبر الهواتف الحقيقية الآن؛ اختبار الأجهزة النهائي في المرحلة 10.
6. العمل على فرع main حسب توجيه صاحب المشروع الحالي؛ لا تنشئ فروع/طلبات دمج بديلة دون طلب.

## أولًا — بوابات تحقق مؤجلة

هذه البنود ما زالت بوابات قبول للمراحل المعنية. يمكن مواصلة تنفيذ مرحلة يحددها صاحب المشروع قبل إغلاقها، لكن لا يجوز إعلان اكتمال المرحلة المرتبطة بها أو ادعاء تحقق لم يحدث.

### A. البناء
- سجل CI المذكور أدناه قديم ولا يثبت حالة commit الحالي. لم تُشغّل عملية بناء أو اختبارات ضمن تنفيذ المرحلة السابعة الحالي.
- تشغيل #43250364735 فشل على مسودة PR #30 غير المدمجة، بسبب تمرير `entry.Key` كنص إلى `datastore.Delete` في خدمة mailbox. لم يكن هذا فشلًا في main. أُغلق PR #30 لأن محتواه بدأ نواقص المرحلة الثالثة قبل موعدها.
- يجب أن يبقى أي فشل مستقبلي مربوطًا بفرعه وcommitه الصحيح، وألا يُنسب إلى main دون تحقق.

### B. جرد main والتوثيق
- استخدم `docs/MAIN_BRANCH_AUDIT_AR.md` كقائمة التنفيذ الحالية.
- README العربي والإنجليزي يجب أن يذكرا ما هو موجود فعلًا وما هو غير مكتمل، بما في ذلك قيود MLS وخصوصية منشورات المجتمعات والنسخ والاستعادة.
- عند كل ميزة جديدة: حدّث README والتوثيق الفني في نفس التغيير.

### C. إغلاق اختبارات المرحلة الأولى — دون إعادة بناء النظام
الموجود في main هو BackupManager/BackupArchive/BackupCrypto وRestoreApplier. لا تستبدلها ولا تنشئ نظام Backup ثانيًا.
المتبقي:
- SQLCipher end-to-end restore integration.
- crash/restart recovery في كل مرحلة من staged swap/rollback.
- consistency بين Room DB وMLS DB المنفصلتين أثناء snapshot.
- migrations فعلية على fixtures لكل نسخة قديمة مدعومة.
- اختبارات تلف/فقد الملفات والمفاتيح والتفضيلات وكلمة المرور الخاطئة والمساحة غير الكافية.
- لا يُعلن إغلاق المرحلة الأولى حتى تُشغّل هذه الاختبارات بنجاح على CI.

### D. إكمال تنسيق MLS
- الموجود: OpenMLS 0.9.2 عبر Rust/JNI؛ KeyPackage/Welcome/Commit/ApplicationData؛ حفظ epoch؛ إضافة/إزالة الأعضاء؛ طلبات مشرفين عبر المالك؛ المالك الوحيد ككاتب epoch؛ مرفقات MLS؛ إيصالات قراءة RELYRA control.
- المتبقي: RFC 9420 Proposal coordination بين عدة مشرفين، الدمج/الرفض الحتمي للمقترحات المتزامنة، معالجة fork/replay/conflicting commits، واختبارات إعادة التشغيل والتوافق.
- لا تستبدل OpenMLS أو تبنِ بروتوكول MLS جديدًا. أكمل السلوك الناقص فوق التنفيذ الحالي.

**يظل إغلاق هذه البوابات شرطًا لإعلان اكتمال العمل الذي تغطيه؛ لا يمنع تنفيذ مرحلة لاحقة بطلب صريح من صاحب المشروع.**

## ثانيًا — المراحل الجديدة بالترتيب

### المرحلة 4 — المكالمات الصوتية والمرئية
- CallEngine يحتوي على WebRTC MediaTracks للصوت والفيديو، وإشارات مكالمات موقعة، وقبول/رفض/إنهاء وتحكم بالميكروفون والكاميرا.
- المكالمات مرتبطة بواجهة المحادثة والإشعارات وخدمة foreground المناسبة.
- ما زال التوافق بين هواتف مستقلة والتحقق من ظروف الشبكة والأذونات الفعلية ضمن اختبارات المرحلة 10.

### المرحلة 5 — تعدد الأجهزة
- الموجود: اقتران يدوي موقع وموافقة، مفاتيح منفصلة لكل جهاز محفوظة عبر Keystore، شاشة لإدارة الأجهزة والإلغاء، ومزامنة مشفرة لبيانات محددة عبر Relay مع معالجة تعارضات وإيصالات.
- المتبقي: مزامنة تلقائية كاملة للرسائل وسجل المجموعات/MLS والمرفقات وحالة Ratchet، نموذج آمن لتفويض المفتاح الجذري، وانتشار الإلغاء والتحقق على جميع مسارات الإرسال، ثم اختبار هواتف مستقلة.

### المرحلة 6 — Mesh دون إنترنت
- الموجود في المصدر: BLE GATT اختياري منفصل عن Bluetooth Classic، توقيع مصدر الرسالة وكل قفزة، TTL بحد أقصى 24 ساعة، حد 8 قفزات، منع الحلقات والتكرار، وطابور محلي مشفر بموافقة مرحّل منفصلة وحصة تخزين محددة.
- توجد اختبارات وحدات لترميز envelopes وإيصالات التسليم؛ لكن لا يوجد إثبات لتوافق Mesh متعدد الهواتف أو ثبات العمل بالخلفية أو التسليم النهائي على أجهزة فعلية.

### المرحلة 7 — التكاملات
- **منفذ جزئيًا:** Local API قراءة فقط على loopback مع Bearer token مؤقت 15 دقيقة وصلاحية اختيارية لقراءة الهوية العامة.
- **منفذ جزئيًا:** Plugin workflow runtime محدود بصيغة JSON، مع قائمة أوامر مسموح بها، موافقة صريحة على الصلاحيات، تثبيت معطل افتراضيًا، وسجل نشاط محلي محدود. لا ينفذ كودًا عامًا.
- **غير منفذ:** جسور Matrix وXMPP/OMEMO؛ يجب تنفيذ التشفير وحدود الثقة فعليًا قبل إعلانها.
- **غير منفذ:** IPFS وربطه بالمرفقات المشفرة وتبادل مفاتيحها؛ يجب أن يظل اختياريًا.
- توجد شاشة إدارة للتكاملين المنفذين بالعربية والإنجليزية.
- تفاصيل المصدر والقيود: [حالة المرحلة السابعة](PHASE7_INTEGRATIONS_AR.md). لا تعلن المرحلة مكتملة قبل تنفيذ الجسور وIPFS والتحقق منها.

### المرحلة 8 — الأدوات المرافقة
- Server Studio لإعداد خدمات RELYRA وتشغيلها ومراقبتها وتحديثها وقراءة سجلاتها وإدارة النسخ.
- Desktop/Node tools للاتصال عبر API موثقة وآمنة.
- Developer Tools لتشخيص البروتوكولات وإدارة plugins وقراءة سجلات منقحة.
- ربط كل أداة بالخدمات الفعلية وإظهار حالة الخدمة الحقيقية وعدم إظهار أزرار لا تنفذ شيئًا.

### المرحلة 9 — التدقيق قبل الأجهزة
- SBOM آلي وتدقيق تراخيص كل الاعتماديات المباشرة وغير المباشرة.
- مراجعة أمنية مستقلة للتشفير والمفاتيح والتخزين والشبكة وواجهات API والإضافات.
- تدقيق RTL وإمكانية الوصول وقارئات الشاشة والتباين وتكبير النص.
- reproducible builds، توقيع الإصدارات، حماية سلسلة التوريد، وتحديث سياسة الإفصاح الأمني.
- إغلاق كل نتائج التدقيق الحرجة والعالية أو توثيق قبول مخاطرها.

### المرحلة 10 — اختبار الأجهزة الحقيقية
- عدة هواتف مستقلة وهويات منفصلة، إصدارات Android مختلفة.
- الرسائل الفردية والمجموعات وMLS والمرفقات والنسخ والاستعادة والمكالمات وتعدد الأجهزة.
- Wi-Fi وبيانات الهاتف وNAT مقيد وTURN وقطع الشبكة والتجوال.
- العمل بالخلفية والبطارية وإيقاف العملية وإعادة التشغيل والتحديث.
- توثيق الجهاز والشبكة والخطوات والنتيجة لكل حالة؛ إصلاح وإعادة اختبار كل عطل.

## ثالثًا — المرحلة الثالثة مؤجلة حتى بعد 4–10

لا تنفذ أيًا من هذه البنود قبل إتمام المراحل 4–10:
- DHT موزع متعدد العقد، ومقاومة replay/rollback لسجلات الحضور.
- دليل مجتمعات موزع/متكرر عبر DHT بدل فهرس محلي وحيد.
- تكامل TURN فعلي واختبارات allocation وnonce وrate limit عبر restart/instances.
- تشخيص لكل محاولة توجيه: connector، النتيجة، الزمن، سبب الفشل.
- Store-and-Forward عبر عقد طرف ثالث بموافقة المالك وحدود TTL والتخزين والحذف.
- نشر بنية عامة متعددة المشغلين؛ المستودع لا يستضيف خدمة عامة للمستخدمين.

## بوابة قبول كل مرحلة
لا تنتقل تلقائيًا للمرحلة التالية إلا بعد:
1. تنفيذ جميع مخرجات المرحلة في الكود.
2. ربط كل أداة وخدمة بواجهات التطبيق ذات الصلة.
3. إضافة اختبارات نجاح وفشل وإعادة تشغيل/تعارض حسب الميزة.
4. تحديث README العربي والإنجليزي ووثائق التصميم والجرد.
5. نجاح CI على commit النهائي.
6. توثيق صريح لما يحتاج أجهزة حقيقية في المرحلة 10.

راجع [جرد main](MAIN_BRANCH_AUDIT_AR.md) قبل أي تعديل حتى لا يتكرر تنفيذ شيء موجود.
