# المرحلة التاسعة — تدقيق الأمان وسلسلة التوريد والإصدار

**حالة التنفيذ:** أُضيفت أدوات التدقيق والأتمتة إلى المستودع. وجود الأدوات لا يعني أن مراجعة أمنية مستقلة أو موافقة قانونية على التراخيص أو توقيع إصدار إنتاجي قد اكتمل. نتائج التشغيل والأدلة تحفظ كـ GitHub Actions Artifacts، وتظل المراجعات البشرية بوابات قبول إلزامية.

## 1. جرد مكونات البرمجيات SBOM

- يولّد CycloneDX ملف SBOM مجمعًا من اعتماديات Gradle التي تم حلها فعليًا، بما فيها الاعتماديات غير المباشرة.
- يولّد Syft ملفات CycloneDX مستقلة لخدمة Go ومكتبة Rust وأداة Node بعد التحقق من بصمة إصدار Syft المثبت.
- يحفظ Workflow ملفات SBOM كـ Artifacts.
- يجمع script مكونات جميع الملفات ويخرج تقرير JSON وMarkdown للتراخيص وبياناتها الناقصة.

## 2. مراجعة التراخيص

يعرض التقرير حالتين:
- IDENTIFIER_FOUND: عُثر على معرّف ترخيص، ولا يعني ذلك اعتماد التوافق القانوني.
- REVIEW_REQUIRED: بيانات الترخيص ناقصة أو تنتمي إلى عائلة تحتاج مراجعة خاصة بالتوزيع.

**مسألة معروفة:** اعتماد smack-omemo-signal موضح في Gradle على أنه GPL-3.0. تقرير آلي لا يحسم أثر الربط أو التوزيع؛ يجب توثيق قرار قانوني قبل نشر ملفات ثنائية. لا يحذف التدقيق هذا الاعتماد تلقائيًا ولا يستبدله.

## 3. فحص الثغرات وسير العمل

- تم رفع Toolchain Go إلى 1.26.11 وتثبيت `golang.org/x/net` على 0.60.0.
- يصدر govulncheck نتائج بصيغة JSON. السكربت `scripts/audit_go_vulns.py` يرفض أي نتيجة غير معروفة، ويشترط مراجعة يدوية لتنبيه GO-2024-3218. قاعدة Go الرسمية تعتبر كل الإصدارات متأثرة ولا تسجل إصلاحًا معروفًا، بينما نشرة GitHub التي تمت مراجعتها تحدد الإصدارات المتأثرة حتى `0.20.0`؛ النسخة المستخدمة في RELYRA هي `0.43.0`. بسبب تعارض المصدرين، يسجل السكربت `REVIEW_REQUIRED` ويبقي بوابة الأمان حمراء بدل اعتبار الإصدار الأحدث آمنًا تلقائيًا.
- شجرة MLS مثبتة على مراجعة OpenMLS Git التالية: `6100df3fb1d8c3eeab53e349fcbd621f98c44fe2`. ترفع `libcrux-kem` إلى 0.0.10 و`crypto-bigint` إلى 0.7.6، وتستخدم `rusqlite 0.42.0 / libsqlite3-sys 0.40.0` مع SQLCipher 4.20.0 وSQLite 3.54.1 المدمجين. يعالج ذلك ثغرتي توقف Libcrux ومشكلة ثبات توقيت الحسابات وثغرة SQLite دون إسقاط SQLCipher أو تعطيل التشفير.
- يظل `proc-macro-error2` تحذير عدم صيانة من RustSec مصدره `hax-lib-macros` ضمن سلسلة Libcrux؛ لا توجد له نسخة إصلاح معلنة. وهو ليس ثغرة أمنية بحد ذاته، وسيظل ظاهرًا بدل إخفائه.
- يفحص cargo audit شجرة Rust مقابل قاعدة RustSec.
- يحلل zizmor ملفات GitHub Actions.
- تم تثبيت Actions الرئيسية إلى commit SHA وتعطيل حفظ بيانات اعتماد checkout.
- يتابع Dependabot اعتماديات Gradle وGitHub Actions وGo Modules وCargo.

تمر بوابة التدقيق فقط بعد إصلاح النتائج أو مراجعة انطباق موثقة مرتبطة بالإصدار. هذا لا يثبت غياب كل المخاطر الممكنة. وتظل مخاطر Sybil وحجب سجلات DHT مسألة معمارية وتشغيلية منفصلة تتطلب مشغلين مستقلين.

## 4. قفل الاعتماديات والتحقق من البصمات

ينشئ Workflow ملفات bootstrap التالية:
- gradle.lockfile وapp/gradle.lockfile لحالات اعتماديات Gradle.
- gradle/verification-metadata.xml لبصمات SHA-256 للحزم المحلولة.
- Cargo.lock لشجرة Rust.
- go.sum لوحدات Go.

ترفع الملفات كـ Artifact للمراجعة؛ لا تُعتمد تلقائيًا في main. يجب مراجعتها ثم إضافتها إلى المستودع، وعدم الثقة عميانيًا بأول حل اعتماديات. قفل الإصدار والبصمة يثبتان تكرار نفس الملفات بعد المراجعة، ولا يثبتان أن مصدر الحزمة آمن عند أول تنزيل.

## 5. قابلية إعادة البناء

ينفذ Workflow بناءين نظيفين متتاليين لـ APK debug على نفس صورة runner ونفس سلسلة الأدوات، ثم يقارن SHA-256. تطابق الملفين دليل قابلية تكرار داخل تلك البيئة فقط؛ لا يمثل إثباتًا بين مضيفين مستقلين أو أنظمة تشغيل مختلفة.

## 6. توقيع إصدار الإنتاج وإثبات المصدر

أُضيف Workflow يدوي لتوليد APK release موقّع والتحقق من التوقيع، ثم إصدار provenance attestation.

يتطلب تشغيله إضافة الأسرار التالية يدويًا إلى إعدادات GitHub Actions في المستودع:
- RELYRA_RELEASE_KEYSTORE_BASE64
- RELYRA_RELEASE_STORE_PASSWORD
- RELYRA_RELEASE_KEY_ALIAS
- RELYRA_RELEASE_KEY_PASSWORD

مفتاح التوقيع لا يضاف إلى Git، ويُخزن مؤقتًا في runner بصلاحيات مقيدة ويُحذف بعد الوظيفة. لم يُنشأ إصدار موقّع حتى يضيف مالك المستودع المفتاح والأسرار ويشغل Workflow بنجاح. APK debug ليس إصدارًا إنتاجيًا موقّعًا.

## 7. تدقيق RTL وإمكانية الوصول

- التحقق من تطابق مفاتيح الموارد العربية والإنجليزية موجود ضمن فحص المشروع.
- أضيف فحص ساكن مبدئي لعناصر IconButton التي تحتوي أيقونة دون نص، ولعناصر الصور القابلة للنقر التي تفتقد وصفًا صوتيًا.
- نتائج الفحص تلميحات للمراجعة وليست شهادة وصول. ما زال يلزم اختبار TalkBack وترتيب التركيز والتباين وتكبير النص واتجاه القراءة RTL وأحجام اللمس يدويًا.

## 8. مراجعة أمنية مستقلة — ما زالت مطلوبة

لم تُجرَ مراجعة مستقلة من طرف ثالث للتشفير وإدارة المفاتيح والتخزين المشفر وMLS والنقل والشبكة وLocal API وعزل الإضافات. الأتمتة تجهز قائمة المكونات والأدلة وتكشف بعض المخاطر المعروفة لكنها لا تستبدل مدققًا مستقلًا. يجب تسجيل كل نتيجة مع شدتها وأثرها والنسخة المتأثرة وخطوات إعادة الإنتاج والإصلاح وإعادة الاختبار.

## بوابات قبول المرحلة التاسعة

تظل المرحلة مفتوحة حتى:
1. مراجعة ملفات lock والبصمات وإضافتها إلى المستودع.
2. فرز نتائج الثغرات وتحليل GitHub Actions ومعالجة المخاطر أو قبولها رسميًا.
3. إغلاق ملاحظات إمكانية الوصول بعد الاختبار اليدوي.
4. مراجعة كل التراخيص، بما فيها اعتماد Smack Signal OMEMO.
5. نجاح مقارنة البناء على بيئتين مستقلتين، وليس runner واحد فقط.
6. إتمام مراجعة أمنية مستقلة وإغلاق الملاحظات الحرجة والعالية أو قبولها رسميًا.
7. إضافة أسرار توقيع الإصدار وتشغيل Workflow بنجاح والتحقق من APK وattestation.
